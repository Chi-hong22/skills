# Project Log 内部日志合同

本文档是 `project-log` Skill 的内容权威。项目生成的 `.log/README.md` 只是本合同的精简副本，用于离线阅读和降级执行。

## 1. 目标

项目日志应能够还原：

1. 为什么推进某项工作。
2. 当时采用了什么思路、假设和方法。
3. 获得了什么可复核数据或工程证据。
4. 证据如何改变工程或研究判断。
5. 结论能说到哪里，不能说到哪里。

日志既要保障工程连续性，也要为论文中的问题动机、方法演化、实验设置、负结果和讨论边界保留可追溯材料。

日志必须自包含：脱离原项目也能梳理出核心变化。短正文完整留痕；长正文以主体概述承载核心，细节原文以指针可定位。

## 2. 节点定义

一个日志节点等于一次可独立复核的工程或项目认知状态转移：从问题、目标或假设开始，以证据支持的结果、决策或边界结束。

不要按以下对象机械拆节点：

- 一次 commit。
- 一个文件。
- 一次 Agent 会话。
- 一轮 RED/GREEN/回归。
- 一次 README 或索引同步。

### 必须拆分的信号

- 成功标准不同。
- 证据等级不同，例如局部验证与全量验证。
- 工作阶段从实现进入实验、从实验进入诊断、从诊断进入裁决。
- 证据状态发生变化。
- 一个问题已经修复，另一个问题仍是待验证假设。
- 出现可独立复用的负结果、反证、根因或 no-go。

### 应合并的信号

- 多个 commit 共同实现同一个可观察行为。
- 多个文件共同组成同一个接口或状态变化。
- 测试、文档和索引只是主功能的伴随同步。
- 临时错误未改变设计、数据或结论。

## 3. 类型枚举

日志中写英文标签，并紧随中文含义：

| 英文标签与中文含义 | 使用条件 |
|---|---|
| `implementation（功能实现）` | 形成或改变可观察工程能力 |
| `bug（缺陷修复）` | 复现、定位并修复错误或性能退化 |
| `experiment（实验）` | 用数据检验研究问题、假设、A/B 或消融 |
| `tuning（参数调优）` | 在约束和指标下比较参数候选并裁决 |
| `decision（决策）` | 架构、接口、研究口径或路线取舍 |
| `no-go（否决）` | 证据表明当前路线不应继续，需记录停止和重开条件 |
| `docs（文档契约）` | 文档变化改变合同、验证策略、claim、术语边界或复现路径 |
| `maintenance（工程维护）` | 不改变核心行为但形成可复核的工程状态变化 |
| `release（发布）` | 形成可交付、可识别的版本节点 |

普通文档同步、格式调整、索引更新不使用独立 `docs（文档契约）` 节点，在主节点末尾一句带过或省略。

## 4. 证据状态枚举

| 英文标签与中文含义 | 判定 |
|---|---|
| `provisional（暂定）` | 已有初步证据，但尚未达到项目声明或验收标准 |
| `verified（已验证）` | 已按项目约定的验证等级取得满足标准的结果 |
| `no-go（已否决）` | 证据支持停止当前路线；必须写明反证、停止和重开条件 |
| `superseded（已被取代）` | 后续证据、实现或正式概念已取代本节点，但其历史因果仍有效 |
| `git-backfill（Git 历史补录）` | 节点来自 Git 可见事实，思路和学术判读可能不完整 |

证据状态不是进度百分比。只有验证等级满足项目合同，才能使用 `verified（已验证）`。

## 5. 实质性节点格式

```markdown
#### YYYY-MM-DD：正式节点名称

- **节点 ID**：LOG-YYYYMMDD-NN
- **类型**：experiment（实验）
- **证据状态**：verified（已验证）
- **目标或问题**：本节点要解决或判定什么。
- **背景与基线**：触发原因、旧行为、已有基线或前置限制。
- **思路或假设**：为什么选择当前方向；要检验的机制或判断。
- **实施或方法**：关键 seam、方法、控制变量或最小修复，不逐文件记账。
- **修改正文**：修改的内容本体。≤10 行完整写入，多行使用缩进引用块；>10 行写 3-5 句主体概述并附细节原文指针。
- **数据与证据**：数据范围、配置、指标、原始数值、异常样本、验证等级和证据路径。
- **结果**：客观发生了什么，区分成功、失败和未观察到差异。
- **判读与决策**：数据支持或反驳什么；因此采用、拒绝或延后什么。
- **边界与未验证项**：结论适用范围、风险、缺失证据和不能宣称的内容。
- **研究含义**：可选；仅在证据确实改变研究假设或 claim 时填写。
- **关联**：前置/后续/取代节点、commit、issue、PR、数据和复现入口。
```

核心证据链不能缺少：

```text
目标 → 思路 → 证据 → 判读 → 边界
```

`修改正文` 补充内容本体，不替代证据链。它与 `实施或方法` 的分工：

- `实施或方法`：怎么做的——关键 seam、设计取舍、控制变量或最小修复。
- `修改正文`：做出来的内容本体——论文定稿文字、代码的核心逻辑/含义、合同或配置的定稿内容。

`修改正文` 的长短判据：

- ≤10 行：完整写入；多行使用缩进引用块（`  > 行内容`）。
- >10 行：写 3-5 句自包含的主体概述，并附细节原文指针（`路径 §位置 @ commit`；未提交时省略 commit 并标注“未提交”），可选附 ≤3 行关键句摘录。
- 修改正文不是逐文件 diff、完整代码转储或文件清单；细节差异由 Git 承载，日志保存核心逻辑与含义。

字段可以简短，但不能用“修改若干文件、测试通过”代替证据链。信息确实不存在时，明确写“未记录”“无法从现有证据恢复”或“不适用”。

## 6. 分类型要求

`修改正文` 必填于 `docs（文档契约）` 与 `implementation（功能实现）`；`experiment（实验）`、`tuning（参数调优）`、`bug（缺陷修复）` 可选；`git-backfill（Git 历史补录）` 可选，仅当能由可见 diff 可靠概括核心逻辑/含义时填写。

### implementation（功能实现）

至少记录：工程问题、关键设计思路、输入/输出/状态或接口行为变化、关键取舍、正常与边界路径验证、未覆盖范围。

### bug（缺陷修复）

至少记录：可观察现象、复现条件、根因证据链、根因与症状的区别、最小修复、回归验证，以及对历史数据或实验可信度的影响。

### experiment（实验）

至少记录：研究问题或假设、数据集和版本、样本范围、baseline、treatment、控制变量、配置、指标定义、原始数值、异常样本、判读、适用范围、复现入口。

不能只写“效果提升”“实验成功”或“结果更好”。

### tuning（参数调优）

至少记录：硬约束、成功门槛、候选范围、候选矩阵或关键数值、主评价指标、选择/拒绝理由、适用数据范围、是否允许进入更高成本验证。

若所有候选均失败，形成 `no-go（否决）` 节点，不以无证据继续扫参替代裁决。

### decision（决策）

至少记录：原问题、备选方案、关键证据、权衡、采用和拒绝的方案、对接口/架构/claim 的影响，以及重审条件。

### no-go（否决）

至少记录：失败门槛、反证、停止理由、仍保留的能力、不能再宣称的内容、重新开启路线所需的新证据。

### docs（文档契约）

只在文档改变工程合同、验证策略、架构语义、术语边界、论文 claim 或复现路径时独立记录。写清“改变了什么语义”和“是否改变代码或实验结论”，不列出全部文档文件。

### maintenance（工程维护）与 release（发布）

记录可观察状态、范围、验证和边界。依赖升级、生成物、锁文件或发布资产仍遵循项目自身变更规则。

## 7. 临时表述生命周期

开发中可以在 `.log/active.md` 暂时使用 `方案1`、`方案2`、`方法A`、`临时路径` 等工作名，但应显式标注为临时命名，并在稳定前完成语义收口。

### 修改

若只是措辞不准确、概念不变，直接修改 active 中的表述为更准确名称。不要为纯文字修订创建日志节点。

### 升级

若临时概念形成稳定接口、方法、实验因素或论文术语：

1. 赋予正式、可区分的名称。
2. 将有效的目标、思路、方法、数据和判读整理进正式节点。
3. 在首次出现处可写一次“原临时称为……”，之后只使用正式名称。
4. 同步正式文档时，只记录语义和证据变化，不记录逐文件操作。

### 合并

若多个临时记录实际描述同一个状态转移：

1. 选择一个正式节点作为主节点。
2. 合并各记录中的有效思路、数据、异常和判读。
3. 删除重复描述、冲突占位符和已经失效的文字。
4. 保留原节点 ID 或 commit 作为关联，避免证据链断裂。

### 删除

若临时表述纯属重复、错字、无效占位且没有影响实现、实验或决策，可以从 active 删除，不留“删除了某段文字”的流水账。

若旧方案曾影响项目路线、产生数据或导致决策，不能从历史因果中抹去：

- 被新方案取代时标记 `superseded（已被取代）`，并关联替代节点。
- 被证据否决时标记 `no-go（已否决）`，并保留反证和重开条件。
- 已归档节点原则上不回写；新增修正或取代节点。

月结前，active 不应残留没有解释的 `方案1`、`方法A`、`TODO 命名` 等临时占位。

## 8. 流水账压缩规则

应优先压缩或删除：

- 完整 commit message 列表。
- 逐文件修改清单。
- 未经概括的完整代码转储或完整 diff；差异由 Git 承载，日志只保存核心逻辑与含义。
- 每条测试命令和测试文件的重复罗列。
- README、索引、AGENTS.md、CLAUDE.md 的逐项同步。
- Agent 名称、模型、审核星级和对话过程。
- 对同一事实重复书写“目标、成果、结论”。

推荐写法：

```markdown
- **实施或方法**：在输入校验 seam 增加显式拒绝路径，保持公共接口不变。
- **数据与证据**：正常、边界和失败路径定向测试通过；完整命令见关联 commit。
- **文档同步**：更新入口和术语索引；无新增算法结论。
```

## 9. 因果关系与论文挖掘

节点 ID 应稳定。`关联` 字段优先表达：

- `precedes`：前置节点。
- `validates`：验证的节点或假设。
- `corrects`：修正的节点。
- `supersedes`：取代的节点。
- `follow-up`：直接后续节点。
- `evidence`：数据、图表、脚本或结果入口。

`研究含义` 只在真实数据或机制证据支持时填写，建议使用“该证据支持/反驳……，因此当前 claim……”的具体句式，避免事后拔高学术意义。

## 10. 历史更正

归档默认冻结。发现历史错误时：

1. 新增 `decision（决策）`、`bug（缺陷修复）` 或对应类型的更正节点。
2. 引用被更正节点 ID。
3. 说明旧结论为何失效、新证据是什么、哪些历史结果受影响。
4. 将旧节点视为 `superseded（已被取代）`，不要静默重写历史。
