# 复杂日志任务的 Agent 工作流

本文定义 `project-log` 在复杂迁移、批量补录和语义裁决中的协作方式。目标是把可并行的机械工作交给子 Agents，同时让证据边界、架构判断和最终结论始终由主 Agent 负责。

## 1. 触发条件

出现以下任一情况时采用本工作流：

- 旧日志位于多个路径、使用多种格式或包含重复记录。
- 需要回填多个月份、多个历史阶段或大量 commit。
- 根级或嵌套 `AGENTS.md`、`CLAUDE.md` 与新合同存在冲突。
- `方案1`、`方法A` 等临时表述需要正式命名、合并、否决或建立取代关系。
- 已归档节点需要更正，且可能影响后续结论、数据或论文 claim。
- Schema、模板、托管块或项目侧 `.log/README.md` 需要升级。
- 单个 Agent 难以在一次上下文中同时完成检索、迁移、验证和独立审查。

简单初始化、单节点记录、单月归档或无冲突的定点修正不需要委派。

## 2. 角色边界

### 主 Agent：orchestrator + deep reasoning

主 Agent 负责：

- 确认目标、项目根目录、允许修改范围和成功标准。
- 判断哪些内容属于事实、合理推断或不可恢复信息。
- 设计节点边界、迁移顺序、去重策略和文件所有权。
- 判断旧概念应修改、升级、合并、删除、no-go 还是 superseded。
- 处理证据冲突、历史因果、Schema 兼容和架构语义。
- 综合子 Agent 输出，复核原始证据、diff、验证结果和风险。
- 对最终日志内容、项目提示词和交付声明负责。

主 Agent 不应长期陷入可安全委派的逐 commit 摘要、批量路径扫描、机械字段搬运、重复格式化或同类检查。

### 子 Agents：机械执行与独立检查

子 Agents 可承担：

- 只读检索旧日志路径、月份、节点 ID、完整 commit hash 和提示词冲突位置。
- 按已确定规则提取 Git 元数据、建立候选覆盖表和来源映射草稿。
- 在独占文件范围内执行定点写入、模板生成或批量格式转换。
- 运行 audit、测试、diff check、链接检查和幂等验证。
- 对指定结果做简要独立 review，搜索遗漏、重复、反例和越界声明。

子 Agents 不得：

- 猜测缺失的历史思路、实验解释或学术结论。
- 自行扩大扫描、修改或删除范围。
- 在没有明确文件所有权时与其他 Agent 修改同一文件。
- 代替主 Agent 决定 claim、no-go、superseded、Schema 迁移或冲突取舍。
- 返回冗长过程记录，迫使主 Agent 重新提炼全部内容。

## 3. 拆解与并行原则

按独立输入、独立产物和独立验证拆分，不按“每个 Agent 分一点同一文件”拆分。

适合并行的例子：

- Agent A 只读扫描 legacy 人工日志；Agent B 只读提取 Git 提交；Agent C 只读审查提示词冲突。
- Agent A 写 2024 年归档；Agent B 写 2025 年归档；前提是月份文件完全不重叠，节点 ID 和排序规则已冻结。
- 写入 Agent 完成后，由另一个只读 Agent 独立运行 audit 和 diff review。

不适合并行的例子：

- 多个 Agent 同时编辑 `.log/active.md`。
- 一个 Agent 正在正式命名，另一个 Agent 同时重写同一节点关系。
- 证据边界尚未确定，就让多个 Agent 各自判断 no-go 或论文 claim。

主 Agent 为每个可写子任务分配互斥文件所有权。需要跨文件一致性时，先由主 Agent 冻结 Schema、节点 ID、正式术语和映射规则，再并行写入。

## 4. 委派模板

主 Agent 使用以下模板，删除不适用项但不要省略范围与验证：

```text
任务：<一个边界清晰、可独立完成的子任务>

目标：
- <要得到的事实、产物或检查结论>

输入与证据：
- <允许读取的路径、Git ref、节点或合同>

允许修改：
- <精确文件或目录；只读任务写“无”>

禁止事项：
- 不修改范围外文件。
- 不推断未被证据支持的思路、数据解释或学术结论。
- 不决定 <由主 Agent 保留的语义/架构问题>。

期望输出：
- 按“事实 / 产物或改动 / 验证 / 风险”返回。
- 内容简洁，可被主 Agent 直接合并。

验证方式：
- <命令、数量核对、hash、diff 或人工复核锚点>
```

若子任务涉及写入，再明确编码、换行、节点排序、文件所有权和原子写入要求。

## 5. 子 Agent 固定输出格式

```text
事实
- <由原始文件、Git 或命令确认的事实；附路径/hash/数量>

产物或改动
- <创建或修改的精确文件；只读任务写“无”>

验证
- <执行的检查、结果和失败项>

风险
- <冲突、缺失证据、待主 Agent 裁决项；没有则写“无”>
```

不要把思考过程、完整命令日志或重复文件内容放入返回。关键证据使用可定位的路径、节点 ID、完整 hash、行号或简短原文。

## 6. 主 Agent 复核门

主 Agent 收到子任务结果后逐项检查：

1. 输出是否在委派范围内，是否修改了未授权文件。
2. 事实能否回到原始日志、Git 完整 hash、diff 或测试结果。
3. legacy 人工日志是否优先，是否出现重复补录或低等级证据覆盖高等级证据。
4. 正式术语、节点 ID、双语类型和证据状态是否一致。
5. 思路、数据、判读和边界是否被机械摘要丢失或擅自补造。
6. no-go、superseded、归档更正和 claim 是否由足够证据支持。
7. 多个子任务的文件范围、日期排序、来源映射和关联关系是否冲突。
8. 最终 audit、幂等检查和最小 diff 是否通过。

复核后，主 Agent 明确选择：

- 采纳：证据和产物均满足合同。
- 修订后采纳：机械结果可用，但语义、边界或格式需主 Agent 修正。
- 丢弃：证据不足、越界、冲突或无法可靠合并。

子 Agent 的“完成”不能替代主 Agent 的最终完成声明。

## 7. 典型编排

### 旧日志与大量 Git 历史接管

1. 主 Agent 冻结目标范围、默认 ref、Schema 和去重规则。
2. 子 Agent A 扫描 legacy 人工日志，提取完整 hash 和高价值字段。
3. 子 Agent B 提取 Git 月份、提交和可见验证事实。
4. 子 Agent C 检查提示词、`.gitignore` 和路径冲突。
5. 主 Agent 合并证据，裁决节点边界与不可恢复内容。
6. 按互斥月份文件委派定点写入，或由一个写入 Agent 顺序完成。
7. 独立 review Agent 检查重复 hash、日期、来源映射和边界。
8. 主 Agent 复核并运行最终 audit。

### 临时语义合并或归档更正

1. 子 Agent 只读列出临时别名、节点关系、数值证据和冲突表述。
2. 主 Agent 判断正式名称、有效信息、no-go/superseded 和 claim 边界。
3. 单一写入 Agent 在独占文件中定点修改。
4. 独立 review Agent 核对数值、因果、临时词残留和文档克制度。
5. 主 Agent 决定是否归档或发布更正。
