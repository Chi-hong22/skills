# Git 历史补录规则

Git backfill 用于恢复过去没有写入项目日志、但仍能由仓库证据确认的推进事实。它不是根据最终代码编写一部“看起来完整”的项目故事。

## 1. 核心边界

Git 可以可靠提供：

- commit hash、作者、提交时间和父子关系。
- commit 标题与正文。
- 变更文件和可见 diff。
- 明确写入提交的 issue、PR、测试和验证说明。
- 仓库中的配置、测试、结果摘要和证据文件。

Git 通常不能可靠恢复：

- 当时真正的思路、研究假设和备选方案。
- 数据选择理由、控制变量和未提交的运行条件。
- 原始数值为何具有工程或学术意义。
- 失败结果是否足以形成 no-go。
- 没有写入提交的人工判断、限制和讨论。

不得为满足完整模板而补造这些内容。缺失本身就是 backfill 节点的重要边界。

## 2. 补录前检查

运行 `inspect`，确认：

- 当前路径确实是目标项目根目录。
- 默认分支、当前 `HEAD` 和可达提交范围。
- 仓库是否为 shallow clone。
- 是否存在历史重写、孤立分支或未合并分支。
- 是否已有人工日志、旧日志或 `.log/` 冲突。
- `.log/**` 是否会被 Git 忽略。

默认处理远程默认分支可达历史；无法确定时使用当前 `HEAD` 并明确说明。不要默认扫描所有 refs 或未合并分支；用户可用 `--ref` 指定。

若为 shallow clone，仍可补录可见范围，但必须报告“历史不完整”，不得宣称全量覆盖。

## 3. 证据优先级

按以下顺序处理冲突：

1. 已有人工日志及其明确证据。
2. commit 正文、明确的 issue/PR 和测试说明。
3. commit 标题、日期、作者和可见 diff。
4. Conventional Commit 类型、目录结构和相邻提交关系。

低等级证据不能覆盖高等级证据。代码最终状态不能证明某个历史时间点已经完成验证。

## 4. 节点聚合

节点仍按“可独立复核的工程或认知状态转移”划分，不强制一 commit 一节点。

可以聚合连续提交的条件：

- 明确关联同一 issue/PR/任务 ID。
- commit 正文表明是同一功能的实现、修正和测试。
- 时间连续、scope 一致、变更 seam 高度重合，且不存在不同成功标准。

不得聚合的条件：

- 从实现进入实验或从实验进入裁决。
- 验证等级发生变化。
- 一个提交修复根因，另一个提交只是后续文档或独立问题。
- 合并会掩盖负结果、no-go 或历史回退。

证据不足时，保持紧凑的一 commit 一节点比推断错误的宏大叙事更安全。

## 5. 去重与覆盖

- 已被人工节点明确关联的 commit 不再生成 backfill 节点。
- legacy 人工日志中记录的完整 40 位 commit hash 是最高优先级覆盖键：先据此标记已覆盖提交，再考虑短 hash、标题、日期或文件相似度。
- 新合同中的完整 commit hash 同样是主要去重键；若完整 hash 相同，不因标题或路径变化重复生成节点。
- 短 hash 只有在当前可见历史中唯一解析到一个完整 hash 时，才能升级为精确覆盖；否则只报告歧义。
- 只有相似日期、标题或文件而没有 hash 时，只报告疑似重复，不自动删除。
- 纯 `.log/**`、项目提示词托管块或日志索引修改不生成新的项目推进节点，避免递归日志。
- rebase 导致旧 hash 不可达时，不删除已有人工历史；报告失效关联并等待人工修正。

## 6. 补录节点格式

```markdown
#### YYYY-MM-DD：由提交证据描述的正式节点名称

- **节点 ID**：LOG-YYYYMMDD-NN
- **类型**：implementation（功能实现）
- **证据状态**：git-backfill（Git 历史补录）
- **来源**：Git 历史补录
- **证据完整度**：部分
- **目标或问题**：仅在 commit/issue 明确说明时填写；否则写“现有证据未记录”。
- **背景与基线**：仅写可由前序提交或明确文档确认的状态。
- **思路或假设**：无法从现有证据恢复。
- **实施或方法**：根据 commit 正文和 diff 概括关键行为，不逐文件罗列。
- **修改正文**：可选；仅当可由可见 diff 可靠概括核心逻辑/含义时填写，否则说明无法从现有证据恢复。
- **数据与证据**：commit、可见测试、结果摘要和证据路径。
- **结果**：只写可确认的代码或测试状态。
- **判读与决策**：没有直接证据时写“无法从 Git 历史恢复”。
- **边界与未验证项**：说明缺失的假设、配置、数据、验证等级或结果解释。
- **关联**：commit `<hash>`；issue/PR/相关节点。
```

类型仍使用最符合证据的英文标签及中文含义；证据状态固定为 `git-backfill（Git 历史补录）`。

## 7. 旧日志接管

当项目已有其他位置或格式的人工日志：

1. 先建立只读清单，识别日期、节点和关联 commit。
2. 保留人工日志中的思路、数据、判读和边界，不用 Git 摘要覆盖。
3. 将可确定的人工节点映射到新合同。
4. 用 commit hash 标记已覆盖范围。
5. 只对缺口执行 backfill。
6. 无法可靠转换的旧日志保留原文，并在新索引中说明位置和限制。
7. 在 `.log/README.md` 的“历史来源映射”中登记旧日志来源、覆盖月份、可确认的完整 hash 范围、迁移状态和保留位置。

不要批量“润色”旧节点而改变当时语义。明显的历史错误通过更正或 `superseded（已被取代）` 关系处理。

### 历史来源映射

每个旧日志来源至少登记：

```markdown
| 来源 | 覆盖范围 | Git 覆盖键 | 处理状态 | 保留位置或说明 |
|---|---|---|---|---|
| `Docs/dev-log.md` | 2024-01 至 2024-06 | 完整 hash 12 个 | 已迁移/部分迁移/仅索引 | 原文路径或限制 |
```

- 映射记录来源和处理边界，不复制旧日志正文。
- `Git 覆盖键` 优先记录完整 hash 数量或明确范围；不要把模糊标题写成已确认覆盖。
- 一个来源只完成部分迁移时，写清已覆盖与未覆盖月份或节点。
- 原文仍保留时，记录其位置和只读/冻结状态。
- backfill 或 Schema 升级后同步更新映射，避免后续 Agent 再次扫描或重复迁移同一来源。

## 8. 分月写入

- 当前月份的补录节点写入 `.log/active.md`。
- 已结束月份直接写入 `.log/archive/YYYY-MM.md`。
- 同一日期按可确认的时间或 commit 拓扑排序。
- 大型仓库按月份或提交批次处理，不向 Agent 上下文直接输出完整 Git 日志。

## 9. Dry-run 输出

`backfill --dry-run` 和 `sync --dry-run` 应报告：

- 使用的 ref、起止提交和提交数量。
- shallow clone 或历史不完整警告。
- 已由人工日志覆盖的提交数。
- 将新增、疑似重复、跳过和冲突的节点数。
- 将修改的月份文件。
- 无法恢复的高价值信息类别。

确认预览后再写入。写入后运行 `audit`，检查重复 hash、日期顺序、证据状态和残留占位符。
